## Фаза 3: Django, PWA и брендбук

### Решения:

1. **Бэкенд на Django 6 + DRF.** Правила (матчинг, лимиты, цепочка хэшей, журнал этики)
   перенесены на сервер. Иначе начисления можно подделать из консоли браузера.
   Это осознанное изменение раздела 3.2 мастер-промта («без своего бэкенда») по
   решению команды: продукт должен быть похож на реальную систему, а не на мок.
2. **SQLite в демо, PostgreSQL в плане.** SQLite не требует установки и достаточен
   для защиты; переезд — одна переменная окружения и `DATABASES`.
3. **Сессионная авторизация Django + CSRF.** Без JWT и без сторонних пакетов.
   Пароли — штатный `set_password` (PBKDF2).
4. **Контракт API один:** `GET /api/bootstrap/` отдаёт всё для консоли, действия —
   отдельными командами. Это меньше запросов и проще объяснять.
5. **Два режима фронтенда.** `local` — моки из `src/data` (разработка без сервера),
   `server` — данные из API. Режим определяется автоматически при загрузке `/app/`.
6. **Публичный лендинг на Django-шаблонах.** Консоль — React SPA по `/app/*`.
   Один домен, один вход, никакой CORS-возни.
7. **PWA.** `manifest.webmanifest` + service worker + иконки. Устанавливается на
   Windows/macOS/Linux (Chrome, Edge), Android и iOS. API не кэшируется: реестр и
   матчинг должны быть серверными.
8. **Десктопная консоль — тёмный дашборд по мотивам OpenRouter:** сайдбар с группами,
   верхние вкладки, сводка FinCoin, график по дням, топ действий, тепловая карта
   активности. Мобильный режим остаётся светлым и компактным, как в Mini App.
9. **Брендбук Финуниверситета.** Палитра (Pantone 7687 C / 7711 C и дополнительные
   цвета), шрифты Open Sans + Golos Text, логотип только на контрастном фоне без
   эффектов. Разбор и файлы — в `brand/fa/`.
10. **Проверка Telegram initData реализована** (`core/services/telegram.py`, 4 теста),
    но в демо не включена: по правилам проекта данные Telegram не читаются и не
    сохраняются. Включим при реальной интеграции с ботом.

### Что сделали и почему (простыми словами):

1. Перенесли правила в Python, чтобы их нельзя было обойти через браузер.
2. Сделали публичный сайт и консоль на одном домене — комиссии проще открывать.
3. Добавили установку как приложение — продукт выглядит законченным.
4. Взяли официальные цвета и шрифты университета, чтобы проект не выглядел «чужим».
5. Написали 34 серверных теста — правила FinCoin и этики теперь проверяемы.

### Открытые вопросы:

- Официальные формулировки 10 ценностей (сейчас `official_text = null`).
- Источник цифр 34,7% и 55%.
- Хостинг и домен с HTTPS (обязателен для Telegram и PWA).
- PostgreSQL и боевые настройки (`DEBUG=0`, `ALLOWED_HOSTS`, секреты в env).

## Оптимизация и PWA (итерация 2)

### Что улучшили:

1. **PWA-манифест:** актуальные цвета бренда, `display_override`, `launch_handler`,
   скриншоты для установки (узкий и широкий), короткие ссылки на разделы.
2. **Service worker v2:** в оболочку добавлены манифест, логотип и иконки; API
   по-прежнему не кэшируется. Добавлена обработка `SKIP_WAITING`.
3. **Кэширование ассетов:** хэшированные файлы из `dist/assets` отдаются с
   `Cache-Control: immutable`, HTML консоли — с `no-cache`, чтобы новая сборка
   подхватывалась сразу.
4. **Скорость:** второстепенные разделы (диагностика, траектория, патенты,
   декомпозиция, сценарии) вынесены в ленивые чанки. Основной бандл — 387 КБ
   (119 КБ gzip), чанки 4–14 КБ. Удалены неиспользуемые зависимости: `recharts`,
   `@telegram-apps/sdk-react`, `@tma.js/*`.
5. **Надёжность сброса:** «Сбросить демо» теперь возвращает не только реестр и
   журнал, но и двойника с откликами; у обычного пользователя профиль не
   подменяется демо-студентом.
6. **UI-баги:** откликнутые задачи исчезают из стопки, баннер установки не
   перекрывает разделы (показывается только на главной), добавлен индикатор
   офлайна, видимый фокус для клавиатуры, поднят контраст мелкого текста.

### Что сделали и почему (простыми словами):

1. Приложение ставится и обновляется без ручной чистки кэша.
2. Первый экран грузится быстрее: код редких разделов не мешает старту.
3. Кнопка сброса больше не оставляет «хвостов» от предыдущей демонстрации.
4. Мелкие тексты и фокус стали доступнее — это требование WCAG AA.

## Тестирование и CI

### Решения:

1. **E2E на Playwright** покрывает три сценария защиты: первый месяц первокурсника,
   запрос индустрии и «соблазн лёгких баллов». Перед каждым тестом состояние
   сбрасывается через `/api/demo/reset/`, поэтому прогон повторяем.
2. **Проверка консоли браузера:** тест падает при любой JS-ошибке на странице,
   а не только при отсутствии текста.
3. **Проверка цепочки в серверном режиме** идёт через `/api/ledger/verify/`:
   хэши считает Python (SHA-256), клиентская упрощённая функция используется
   только в локальном демо-режиме.
4. **CSRF-эндпоинт `/api/csrf/`** выдаёт cookie до первого POST — кнопки работают
   сразу после загрузки, без гонки с `bootstrap`.
5. **CI на GitHub Actions:** отдельные джобы для бэкенда, фронтенда и e2e.
   E2E поднимает Django на отдельном порту и собирает свежий бандл.

### Что сделали и почему (простыми словами):

1. Комиссию можно провести по тем же шагам, что проверяет машина.
2. Ошибки в браузере ловятся автоматически.
3. Кнопки не «молчат» в первые секунды после открытия страницы.
4. Каждый push проверяется одинаково — на Windows и на Linux.

## Подготовка PostgreSQL

### Решения:

1. **Одна точка выбора базы** — `api/config/db.py`. Приоритет: `DATABASE_URL` →
   `DB_ENGINE=postgres` + `POSTGRES_*` → SQLite по умолчанию.
2. **Никаких правок кода при переезде.** Меняются только переменные окружения,
   миграции и сид остаются теми же.
3. **`sslmode` из URL** переносится в `OPTIONS`, чтобы облачные базы работали
   без дополнительных настроек.
4. **Драйвер `psycopg` 3** добавлен в зависимости, но SQLite-демо его не требует.
5. **Тесты парсера** (`api/tests/test_database.py`) проверяют URL, алиасы схем,
   абсолютные и относительные пути SQLite и явные `POSTGRES_*`.

### Что сделали и почему (простыми словами):

1. Хостинг можно подключить позже, не переписывая проект.
2. Один и тот же код работает и на ноутбуке, и на сервере с PostgreSQL.
3. Ошибку в строке подключения видно сразу — на тестах, а не на защите.

## Статус API и документация

### Решения:

1. **Статус — из настоящих проверок.** `/status/` бьёт по базе (`SELECT 1`),
   проверяет цепочку SHA-256 демо-студента и наличие сборки консоли. Никаких
   нарисованных графиков: замер пишется только тогда, когда проверка прошла.
2. **Дни без замеров видно честно.** История рисуется за 30 дней, но период до
   первого запуска помечен штриховкой «нет данных», а не 100% uptime.
3. **Замер не чаще раза в минуту.** `StatusSample` пишется с троттлингом:
   страницу можно обновлять сколько угодно, база не растёт.
4. **Таймер systemd вместо отдельного сервиса в compose.** `monitor_ping`
   вызывается через `docker compose exec web python manage.py monitor_ping`
   каждые 5 минут, поэтому история не прерывается ночью. Записи старше 90 дней
   команда удаляет сама.
5. **Документация — данные, а не текст в шаблоне.** `api/web/api_docs.py` хранит
   эндпоинты и навигацию; страница и оглавление собираются из него. Тест
   сверяет, что каждый эндпоинт описан и все якоря существуют.
6. **Параметры эндпоинта — списком, а не таблицей.** На 360 px таблица из четырёх
   колонок нечитаема, поэтому поле, тип и обязательность показываются строкой.
7. **`/api/health/` остался дешёвым.** Он не трогает базу и годится для
   балансировщика; тяжёлые проверки живут только в `/api/status/`.

### Что сделали и почему (простыми словами):

1. Комиссия видит не картинку, а работающую проверку — и может нажать «Проверить сейчас».
2. Мы не выдаём выдуманные 99,99% за реальные: пустые дни так и подписаны.
3. Нагрузка на базу предсказуема: одна запись в минуту вместо одной на каждый запрос.
4. История не рвётся, даже если ночью сайт никто не открывал.
5. Документация не расходится с кодом: правится один файл.
6. На телефоне карточка эндпоинта читается без горизонтальной прокрутки.
7. Быстрый health-эндпоинт не мешает мониторингу и не грузит базу.

## Демо-профили и админка

### Решения:

1. **Партнёр — отдельный аккаунт, а не флаг.** Раньше роль переключалась в состоянии
   фронтенда и общим PATCH. Теперь в сиде два пользователя: `demo` (студент) и
   `partner` (Марина Соколова). Переключение — вход в другой аккаунт через
   `/demo-login/partner/`, со своей сессией, двойником и кабинетом.
2. **Партнёру не начисляется FinCoin.** У него нет реестра, а сброс демо удаляет
   записи, а не создаёт стартовые: вклад индустрии измеряется не монетами студента.
3. **Сброс демо больше не меняет роль.** Иначе партнёр после «Сбросить демо»
   превращался в студента в базе, хотя интерфейс продолжал показывать партнёра.
4. **Платёжеспособность профиля сохраняется в `PATCH /api/me/`.** Добавлены
   `interests` и `weeklyHours` — их же использует матчинг (interestFit, loadFit),
   поэтому редактор профиля влияет на подбор задач, а не только на внешний вид.
5. **Админка — своя `AdminSite`.** Порядок разделов задан вручную (ценности →
   правила → модули → задачи → отклики → двойники → реестр → журнал → барьеры →
   инциденты → мониторинг), заголовки и стартовая страница на русском, на главной
   видны демо-доступы и ссылки на публичные страницы.
6. **Журнал решений ИИ и замеры мониторинга — только чтение.** Журнал, который можно
   править, перестаёт быть журналом; замеры создаёт сервер, а не человек.
7. **Суперпользователь создаётся командой `seed_admin`.** Пароль приходит из
   `ADMIN_PASSWORD`, в репозитории его нет; команда идемпотентна и обновляет пароль
   при повторном запуске.
8. **Ссылку на админку убрали из публичного футера.** Панель — рабочий инструмент
   команды, а не раздел сайта для комиссии; адрес остаётся в README и docs.

### Что сделали и почему (простыми словами):

1. Комиссия видит два настоящих кабинета, а не перекраску одного.
2. Партнёр не «зарабатывает» студенческие монеты — так честнее по смыслу FinCoin.
3. Сброс возвращает демо в исходное состояние и не ломает выбранную роль.
4. Интересы и часы из профиля реально участвуют в подборе задач.
5. Админка читается сверху вниз как рабочий процесс, а не как алфавитный список.
6. Никто случайно не перепишет историю решений ИИ и не подделает uptime.
7. Пароль админки не хранится в коде и меняется одной командой.
8. Публичный сайт не зовёт комиссию в служебную панель.

## Кабинет партнёра

### Решения:

1. **Партнёр — полноценная роль, а не косметика.** Свои эндпоинты `/api/partner/*`,
   свои экраны и своя навигация. Студенческие разделы закрыты и на клиенте, и на
   сервере: отклик, микромодуль и начисление FinCoin возвращают `403`.
2. **Задача принадлежит автору.** У `PartnerTask` появились `owner`, `status` и
   `created_at`; партнёр видит и меняет только свои задачи, демо-задачи закреплены
   за демо-партнёром.
3. **Отклик — это процесс.** У `TaskApplication` есть статус: новый → в шортлисте →
   приглашён → отклонён. Партнёр ведёт воронку, студент видит решение без
   комментариев; статус сохраняется сразу.
4. **Закрытый набор честно закрыт.** Задача со статусом `closed` не появляется
   в ИИ-свате: сервер отвечает «набор на эту задачу закрыт», а не просто прячет её
   в интерфейсе.
5. **Партнёр не зарабатывает FinCoin.** У него нет баланса в шапке и реестра;
   сброс демо не создаёт ему студенческие начисления.
6. **Демо-данные для воронки.** Три соискателя с непригодным паролем и стартовые
   отклики: кабинет партнёра не пустует на защите, но войти под ними нельзя.
7. **Форма задачи показывает результат.** Справа живой предпросмотр карточки:
   партнёр видит, как задача выглядит для студента, ещё до публикации.
8. **Ползунки компетенций — свой стиль.** Нативный range в Chrome рисовал чёрную
   полосу; добавлен класс `.range`, одинаковый в Chrome и Firefox.

### Что сделали и почему (простыми словами):

1. Партнёр и студент — два разных кабинета, а не один с переключателем.
2. Чужие задачи нельзя испортить: меняет только автор.
3. Отклики не теряются: у каждого понятный статус.
4. На закрытую задачу нельзя откликнуться даже через API.
5. Монеты — механика студента, у индустрии другая мотивация.
6. На демо в кабинете партнёра есть живые отклики и воронка.
7. Ошибку в тексте задачи видно до публикации.
8. Ползунки выглядят одинаково на всех машинах комиссии.

## Кабинет партнёра: доработка по практике партнёрских порталов

### Решения:

1. **У партнёра нет курса.** В профиле и модели появились `organization` и `position`;
   поле курса у партнёра скрыто, а `PATCH /api/me/` с `course` возвращает 400.
   Курс — студенческая характеристика, у индустрии её нет.
2. **Партнёрская панель показывает воронку, а не только список.** По практике
   партнёрских порталов (Nintex, JourneyBee) главное — видимость пайплайна:
   добавлены средний матч, доля приглашённых и блок «Требует внимания»
   (новые отклики, задачи без откликов).
3. **Фильтр по статусу отклика.** Партнёр отбирает «новые» или «в шортлисте»
   одним кликом, не листая всю ленту.
4. **Отклики видны на уровне задачи.** На странице задачи — список кандидатов
   с процентом совпадения и сменой статуса: решение принимается там, где задача.
5. **Название партнёра в задаче берётся из организации.** Если организация не
   заполнена — из имени, иначе «Партнёр (пример)». Не выдумываем компанию.

### Что сделали и почему (простыми словами):

1. Партнёр заполняет организацию и должность, а не выдуманный курс.
2. Кабинет отвечает на вопрос «что происходит с моими задачами», а не «вот список».
3. Не нужно искать новые отклики в общей ленте.
4. Кандидатов видно прямо в задаче — как в реальных порталах.
5. В карточке задачи стоит организация партнёра, а не его личное имя.
